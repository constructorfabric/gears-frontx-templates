# FrontX design guardrails

Template version: `0.1.0-alpha.5`\
UI base: `@gears-frontx/ui-kit`  
Scope: interface generation and advisory design review

The YAML front matter above names the kit's design tokens (`colors`, `typography`, `rounded`, `spacing`, `motion`, `controls`, `elevation`), each as the `var(--name)` of a custom property the kit theme declares, and the kit components that use them, written as references such as `{colors.primary}`. It holds names only: the values live in the installed kit theme and in the product theme, and one `var()` covers both light and dark. Its `version` is the kit version the names were taken from. After a kit upgrade, run `node .frontx/ai/@gears-frontx/template-design-guardrails/skills/frontx-design/scripts/check-design-md.mjs` from the project root and add or drop the names it reports. How to read and review it: `.frontx/ai/@gears-frontx/template-design-guardrails/skills/frontx-design/references/design-md.md`.

## The design skill

Every visual task starts with the one design skill, `frontx-design`, at `.frontx/ai/@gears-frontx/template-design-guardrails/skills/frontx-design/`. Its `SKILL.md` is a short map: the binding essentials, which reference to load for each task (theme, build, place, review, verify, DESIGN.md, handoff), and every file the skill holds. Paths below are relative to that directory.

- `references/`: the procedures and the topic rules (layout, tokens, typography, colour, motion, components, accessibility, data display, compositions).
- `rules/`: the machine-readable rules. `rules/quality-gates.json` is the one rule registry; when sources disagree, `sourcePrecedence` in `rules/design-contract.json` is the one order.
- `templates/`: the state inventory and the handoff every task closes with.

Before building a screen, inspect the installed FrontX templates and the existing application, and read the UI kit's installed `llms.txt` and component docs; they win over this file on component APIs. The screen request selects content and behavior; it does not authorize a new visual system.

Rules marked **MUST** are required. **SHOULD** rules may be changed only when the implementation records why (in the component's source comment or the change's PR description). **MAY** rules are optional. Each gate in `rules/quality-gates.json` also states whether it can be waived: `never`, `with-reason`, or `finish`.

## Required qualities

- Clear hierarchy and one obvious primary task per screen.
- Token-backed spacing, color, typography, radius, elevation, motion, and state treatment.
- A 4 px base grid with an 8 px primary rhythm: the kit's `--space-*` scale.
- Shared alignment lines, explicit density, and declared wide, medium, and narrow transformations.
- Responsive behavior without shrinking controls or labels into ambiguity.
- Keyboard access, visible focus, semantic HTML, accessible names, useful validation copy, and WCAG 2.2 AA contrast.
- Loading, empty, error, restricted, partial, and success states where data or actions can produce them.
- Real component reuse instead of visually imitated controls.
- Motion that explains state or spatial change, uses the motion tokens, and respects reduced-motion preferences.
- Measurable review evidence: violated rule ID, location, impact, and correction.

## After generation

Review the screen as `references/review.md` describes, in a fresh context. The review is advisory: it returns a one-word verdict, blockers and prioritized corrections but does not stop delivery. When the assembled application is running in dev mode, the browser check in `references/verify.md` turns the review's unverified items (contrast, rendered widths, live states) into observed findings from the runtime design-defect checker this template delivers (the `@gears-frontx/design-verify` workspace package). The package also ships a headless runner, `npm run verify:ui --workspace=@gears-frontx/design-verify`, that drives the checker across a routes × themes × widths matrix over the Chrome DevTools Protocol and emits `findings.json` plus screenshots, so sweep evidence is one command instead of an improvised browser script. Storybook checks, screenshot comparison, and release gates still belong to a separate testing stage.

Install this template into an existing FrontX shell project with `frontx add @gears-frontx/template-design-guardrails <target>`. After installing, run `npm install` (not `npm ci`) once: the shell's committed lockfile predates this template's workspace package, and `npm ci` fails on the out-of-sync lockfile instead of resolving it. In dev the shell reports verify-package load status under `[verify-packages]` and the running checker reports under `[design-defects]`, so absence, breakage, and a clean sweep are distinguishable; if verification cannot proceed, the correct outcome is an explicit environment-unavailable report, not a stalled run.

When authoring or changing a shell theme, follow `references/theme.md`; theme token format is a contract with the UI kit, and violations render as broken components rather than errors.

## Do's and Don'ts

Do:

- Compose screens from kit components; paint them only through the tokens above, such as `{colors.primary}` for the one primary action of a region and `{colors.muted-foreground}` for secondary text.
- Style anything outside kit components with CSS Modules on kit tokens (`var(--space-4)`, `var(--foreground)`).
- Keep chrome on neutral surface and border tokens and put colour on data and status (APP-001).
- Record a pattern the kit lacks as a kit gap and compose it from kit parts.

Don't:

- Restyle UI kit internals or duplicate a kit component with ad-hoc markup.
- Hardcode visual values when a semantic token exists.
- Use color as the only status signal.
- Invent helper copy, decorative cards, gradients, or metrics to fill space.
- Use Tailwind or any other utility-class framework, or home-made utility classes; the global classes the kit itself ships and documents (`@gears-frontx/ui-kit/utilities.css`) are kit surface and allowed. The UI kit is React, Base UI, CSS Modules and CVA; styling outside kit components is CSS Modules on kit tokens.
- Copy an external design system's visual identity. Material, Carbon, Fluent, W3C, and Vercel sources in `rules/source-registry.json` are research references, not replacement themes.

## Responsive

| Width | Device | Expectation |
|---|---|---|
| 1440 CSS px | desktop | Full layout with side-by-side regions. |
| 768 CSS px | tablet | Secondary regions collapse or move below the primary one. |
| 390 CSS px | phone | One column beside the shell's 56 px menu rail; tables become lists or scroll inside their own region. |
| 320 CSS px | reflow floor | No horizontal page scroll (LAY-002). |

Below 768 px the shell menu starts collapsed to its 56 px icon rail beside the screen; only an expanded menu lies over the screen, behind a backdrop. The screen lays itself out for the width left beside the rail. Controls keep their kit sizes at every width; touch targets meet A11Y-002. Each screen declares its region transformations (LAY-001) and is checked at these widths (APP-005).

## Iteration Guide

- Change the look through the kit or a theme (`references/theme.md`), never through this file's front matter. The front matter names tokens, so a product theme that sets new values for them needs no edit here. After a kit upgrade, run the frontx-design skill's `scripts/check-design-md.mjs`, add or drop the names it reports, review the change as its `references/design-md.md` describes, and commit it.
- Change one screen or component at a time and verify it rendered before the next.
- Product-specific design decisions go into the product's own documents, linked from here, not into this template-owned file.

## Known Gaps

- Three kit badge pairs are below 4.5:1 in the light theme, measured on kit `0.4.1`: `{colors.success}` on `{colors.success-soft}` 3.43:1, `{colors.warning}` on `{colors.warning-soft}` 2.00:1 and `{colors.danger}` on `{colors.danger-soft}` 4.28:1. The kit keeps these drawn values on purpose and routes contrast to its designer; do not rely on badge colour alone, and raise the pairs with the kit owner.
- The kit has no generic layout grid or stack component; page layout is composed with CSS Modules on `--space-*` tokens.
- Only the kit's `Table` has a density axis; other components have one density.
- Kit `0.4.1` has no KPI type role; a KPI value takes the display or heading roles (APP-002).
- The `components` map covers the kit components whose colours and sizes a screen most often pairs, not every kit component or state; the installed kit documentation stays the reference for the rest.
- `scripts/check-design-md.mjs` checks names only. Whether a product theme keeps text readable is seen only in the rendered app: real values and contrast come from the verify runner (`references/verify.md`).
