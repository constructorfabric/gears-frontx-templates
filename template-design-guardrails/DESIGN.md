# FrontX design guardrails

Template version: `0.1.0-alpha.5`  
UI base: `@gears-frontx/ui-kit`  
Scope: interface generation and advisory design review

The YAML front matter above is the kit's design tokens (light `colors`, dark `colors-dark`, `typography`, `rounded`, `spacing`, `motion`, `controls`, `elevation`) and the kit components that use them, written as `{group.token}` references. It is generated from the installed kit's `theme.css`; never edit it by hand. Its `version` is the kit version it was generated from. How to regenerate and check it: `.frontx/ai/@gears-frontx/template-design-guardrails/skills/frontx-design/references/design-md.md`.

## Before generating a screen

1. Inspect the installed FrontX templates and the existing application structure.
2. Read the UI kit's installed `llms.txt` and component documentation. Installed package documentation wins over this file when component APIs differ.
3. Start with the `frontx-design` skill: it sets precedence and the surface, and routes to `generate-interface` and its generation workflow.
4. Reuse the installed application shell, UI kit components, semantic tokens, typography ramp, icon family, and existing composition patterns.

## Contract layers

Apply these layers in order. Do not mix them into one improvised style:

1. The installed application, FrontX template manifests, and `@gears-frontx/ui-kit` documentation are the implementation truth.
2. The bundle's machine-readable contracts define non-negotiable quality gates and fallback layout constraints. Token values come only from the installed system.
3. The bundle guidelines define layout, tokens, typography, color, motion, interaction, accessibility, data-display, and composition rules. Which guidelines a screen task loads is routed through `reference-artifacts/guideline-index.json`, generated from each guideline's front matter (`summary`, `tier`, `loadWhen`) by the repository's `scripts/generate-guideline-index.mjs`; the front matter is the source of truth and the index is never edited by hand.
4. The screen request selects content and behavior; it does not authorize a new visual system.

Rules marked **MUST** are required. **SHOULD** rules may be changed only when the implementation records why (in the component's source comment or the change's PR description). **MAY** rules are optional. Each quality gate in `reference-artifacts/quality-gates.json` also states whether it can be waived: `never`, `with-reason`, or `finish`.

## Required qualities

- Clear hierarchy and one obvious primary task per screen.
- Token-backed spacing, color, typography, radius, elevation, motion, and state treatment.
- A 4 px base grid with an 8 px primary rhythm: the kit's `--space-*` scale.
- Shared alignment lines, explicit density, and declared wide, medium, and narrow transformations.
- Responsive behavior without shrinking controls or labels into ambiguity.
- Keyboard access, visible focus, semantic HTML, accessible names, useful validation copy, and WCAG 2.2 AA contrast.
- Loading, empty, error, restricted, partial, and success states where data or actions can produce them.
- Real component reuse instead of visually imitated controls.
- Motion that explains state or spatial change, uses the motion tokens, and respects reduced-motion preferences.
- Measurable review evidence: violated rule ID, location, impact, and correction.

## After generation

Use `review-interface`. The v0.1 review is advisory: it returns blockers and prioritized corrections but does not stop delivery. When the assembled application is running in dev mode, use `verify-interface` to turn the review's unverified items (contrast, rendered widths, live states) into observed findings from the runtime design-defect checker this template delivers (the `@gears-frontx/design-verify` workspace package). The package also ships a headless runner, `npm run verify:ui --workspace=@gears-frontx/design-verify`, that drives the checker across a routes × themes × widths matrix over the Chrome DevTools Protocol and emits `findings.json` plus screenshots, so sweep evidence is one command instead of an improvised browser script. Storybook checks, screenshot comparison, and release gates still belong to a separate testing stage.

Install this template into an existing FrontX shell project with `frontx add @gears-frontx/template-design-guardrails <target>`. After installing, run `npm install` (not `npm ci`) once: the shell's committed lockfile predates this template's workspace package, and `npm ci` fails on the out-of-sync lockfile instead of resolving it. In dev the shell reports verify-package load status under `[verify-packages]` and the running checker reports under `[design-defects]`, so absence, breakage, and a clean sweep are distinguishable; if verification cannot proceed, the correct outcome is an explicit environment-unavailable report, not a stalled run.

When authoring or changing a shell theme, use `create-theme`; theme token format is a contract with the UI kit, and violations render as broken components rather than errors.

## Do's and Don'ts

Do:

- Compose screens from kit components; paint them only through the tokens above, such as `{colors.primary}` for the one primary action of a region and `{colors.muted-foreground}` for secondary text.
- Style anything outside kit components with CSS Modules on kit tokens (`var(--space-4)`, `var(--foreground)`).
- Keep chrome on neutral surface and border tokens and put colour on data and status (APP-001).
- Record a pattern the kit lacks as a kit gap and compose it from kit parts.

Don't:

- Restyle UI kit internals or duplicate a kit component with ad-hoc markup.
- Hardcode visual values when a semantic token exists.
- Use color as the only status signal.
- Invent helper copy, decorative cards, gradients, or metrics to fill space.
- Use Tailwind or any other utility-class framework, or home-made utility classes; the global classes the kit itself ships and documents (`@gears-frontx/ui-kit/utilities.css`) are kit surface and allowed. The UI kit is React, Base UI, CSS Modules and CVA; styling outside kit components is CSS Modules on kit tokens.
- Copy an external design system's visual identity. Material, Carbon, Fluent, W3C, and Vercel sources in this bundle are research references, not replacement themes.

## Responsive

| Width | Device | Expectation |
|---|---|---|
| 1440 CSS px | desktop | Full layout with side-by-side regions. |
| 768 CSS px | tablet | Secondary regions collapse or move below the primary one. |
| 390 CSS px | phone | One column beside the shell's 56 px menu rail; tables become lists or scroll inside their own region. |
| 320 CSS px | reflow floor | No horizontal page scroll (LAY-002). |

Below 768 px the shell menu starts collapsed to its 56 px icon rail beside the screen; only an expanded menu lies over the screen, behind a backdrop. The screen lays itself out for the width left beside the rail. Controls keep their kit sizes at every width; touch targets meet A11Y-002. Each screen declares its region transformations (LAY-001) and is checked at these widths (APP-005).

## Iteration Guide

- Change the look through the kit or a theme (`create-theme`), never through this file's front matter. After a kit upgrade or a theme change, regenerate the front matter and commit it.
- From the project root: `node .frontx/ai/@gears-frontx/template-design-guardrails/skills/frontx-design/scripts/design-md.mjs generate` regenerates the front matter and keeps this body; `check` fails when the front matter has drifted from the installed kit; `lint` reports broken `{refs}`, tokens defined for one theme only, and text and fill pairs below 4.5:1.
- Change one screen or component at a time and verify it rendered before the next.
- Product-specific design decisions go into the product's own documents, linked from here, not into this template-owned file.

## Known Gaps

- `lint` reports three kit badge pairs below 4.5:1 in the light theme: `{colors.success}` on `{colors.success-soft}`, `{colors.warning}` on `{colors.warning-soft}` and `{colors.danger}` on `{colors.danger-soft}`. The kit keeps these drawn values on purpose and routes contrast to its designer; do not rely on badge colour alone, and raise the pairs with the kit owner.
- The kit has no generic layout grid or stack component; page layout is composed with CSS Modules on `--space-*` tokens.
- Only the kit's `Table` has a density axis; other components have one density.
- Kit `0.4.1` has no KPI type role; a KPI value takes the display or heading roles (APP-002).
- The `components` map covers the kit components whose colours and sizes a screen most often pairs, not every kit component or state; the installed kit documentation stays the reference for the rest.
- `design-md.mjs` reads only the kit's own `theme.css` shape and value grammar and stops with exit 2 on anything else: a value outside the grammar (`lab()`, `lch()`, `oklch()`, `light-dark()`, named colours, an empty value, `var()` with a fallback or with spaces inside, `calc()` with multiplication, named font weights, a quoted font name holding `var(`), percentage opacity, `!important` on a declaration beside the tokens, any construct outside the kit's file shape (another rule such as `html` or `:root[data-theme='dark']`, with or without tokens; any other at-rule such as `@property`, `@import`, `@font-face`, other `@media`, `@supports` or `@layer`; nesting; text outside a block; spaces or another case inside an attribute selector), CSS escapes (a backslash anywhere), blocks out of the kit's order, a plain property beside the tokens other than the block's own `color-scheme` (so no `font-size` or `font`), anything in `body, [data-theme]` but `background-color`, `color` and `font-family` as one `var()`, two tokens on one path, and a token name that maps to a `__proto__`, `prototype` or `constructor` path. A themed copy of the kit must keep that shape; the full list is in the frontx-design skill's `references/design-md.md`.
